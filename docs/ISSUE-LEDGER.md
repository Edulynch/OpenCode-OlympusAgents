## Cómo usar este registro

1. **Antes de iniciar una misión**, leer el issue objetivo, su fila y las evidencias enlazadas; comprobar el estado vivo de GitHub. No repetir investigaciones o suites sin un cambio que pueda alterar la decisión.
2. **Preflight de autoridad antes de worktrees/sesiones:** identificar el repositorio objetivo y su identidad antes de writes dependientes. La identidad OlympusAgents clasifica trabajo sobre su fuente; no autoriza alcances ajenos, recursos runtime instalados, efectos Git de alto impacto, configuración global ni publicación. Consultar [filosofía #92](https://github.com/Edulynch/OpenCode-OlympusAgents/issues/92), [worktrees #77](https://github.com/Edulynch/OpenCode-OlympusAgents/issues/77) y [lote #105](https://github.com/Edulynch/OpenCode-OlympusAgents/issues/105).
3. **Una misión de escritura activa por defecto.** Una excepción de writers paralelos exige gates #77/#105 y autorización propia. Las misiones pueden llegar a PR_READY, pero merge/release/cierre de issues son decisiones separadas.
4. **Actualizar únicamente tras un cambio material de gate**: evidencia nueva, bloqueo, decisión del PM, PR, merge, o cierre. Conservar enlace a evidencia, su fecha, ámbito y clase (`VERIFIED`, `REPORTED`, `INFERRED`, `NOT_OBSERVED`, `NOT_RUN`). No convertir una inferencia en aceptación.
5. **Cierre Git explícito:** para cada rama/worktree usado, consignar `KEEP_ACTIVE`, `CLEANUP_READY`, `CLEANUP_BLOCKED` o `REMOVED_VERIFIED`, previa comprobación del estado local, commits únicos, procesos activos y PR. No borrar WIP, untracked, ignored ni refs antiguas automáticamente.

## Handoff mínimo por issue

Al cambiar de gate, actualizar la fila y enlazar un único checkpoint que responda: **CURRENT_STATE → decisión aceptada → evidencia exacta y límites → OPEN_GATE → NEXT_SINGLE_ACTION → autoridad requerida → rama/worktree/PR y CLEANUP_STATE**. Un cierre de misión no impone un nuevo documento ni otro issue. El [#108](https://github.com/Edulynch/OpenCode-OlympusAgents/issues/108) queda reservado para continuidad transversal entre conversaciones; los detalles permanecen en cada issue/PR.

**Regla de autoridad:** este ledger registra decisiones; **no concede** permisos, autorización para implementar, cerrar issues, fusionar, liberar versiones o borrar recursos.
